# chars: 레이어 캐릭터와 화면 배율

시험일 2026-10-18, Godot 4.7.2 stable (official, ed1daf0bf), Windows 11 데스크탑(RTX 5090), SSH 세션에서 Git Bash로 실행. 렌더러 Forward+ (Vulkan 1.4.341).

## 시험한 것

### 1. 레이어 캐릭터 (`chars/layered_character.gd`)

기본 몸 걷기 `base_body_v02_walk.png`(32×32 칸, 줄 남·동·북, 6프레임, 발 y=31) 위에 표식 레이어 하나를 얹는 Node2D.

- 구조: `Rig`(Node2D) 아래 `Body` + 슬롯 `Back`(등: 곡괭이) · `Waist`(허리: 씨앗주머니) · `Float`(떠 있음: 후광). 노드 위치 = 두 발 사이(프레임 바닥 가운데)
- 그리기 순서: 방향마다 순서표(`char_data.gd` `DRAW_ORDER`)대로 `Rig`의 자식 순서를 바꾼다(`move_child`). 곡괭이는 남·동(·서)에서 몸 뒤, 북에서 몸 앞. 주머니·후광은 늘 앞 (brief §5.6)
  - `z_index`는 쓰지 않았다. z_index는 같은 캔버스의 다른 캐릭터·타일과의 순서까지 바꾸므로(뒤로 보낸 곡괭이가 바닥 타일 밑으로 갈 수 있음) 캐릭터 안의 순서는 트리 순서로 정한다
- 표식 위치: v01 첫 프레임에 그린 레이어라 걷기와 같이 남 +4, 동 +3, 북 +4 내린다. 거기에 프레임별 기준점 이동(몸통 표식은 몸통 기준점, 후광은 머리 기준점)을 더한다. 후광(12×5)은 프레임 밖 머리 위(v01 좌표 x10, y−5)에 두고 2~4프레임에서 1px 뜬다(5차 목업과 같음)
- 서쪽: `Rig.scale.x = -1`로 동쪽을 좌우 반전. 프레임 32px가 발 기준 가운데라 반전해도 정수 픽셀에 남는다
- 팔레트 스왑: `chars/palette_swap.gdshader` (canvas_item). 원본 색 10개 → 목표 색 10개(`uniform vec4[16]`), 프레임 안 y 범위(`band`)에서만 바꾼다. 목표 색은 원본의 채도·명도를 두고 색상만 바꿔 8비트로 맞춘다(teal, moss, wine, sky). 캐릭터마다 ShaderMaterial 1개, 몸에만 건다(표식 레이어는 그대로)
- CPU 기준 그림(`chars/compose.gd`): 같은 표(순서·오프셋·반전·팔레트 규칙)로 캐릭터 한 프레임을 이미지로 만든다. GPU가 그린 화면과 픽셀 단위로 비교하는 데 쓴다

### 2. 화면 배율 (`chars/scale.tscn`)

4단계 에셋(`tiles_grass_base_v02`, `altar_v04` 3×3칸, `alchemy_table_v05` 3×2칸, `crops_v03_sheet` 3줄×7칸)과 캐릭터 4명을 16px 격자에 놓고, 카메라를 가운데에 둔 장면.
진짜 루트 창의 `content_scale_size`(480×270 / 640×360)와 창 크기(1920×1080 / 2560×1440 / 3840×2160)를 바꿔 가며 Godot가 실제로 쓰는 배율(`Window.get_final_transform()`)을 읽고, 내부 렌더 타깃을 읽어 CPU로 그린 같은 장면과 비교했다.

## 명령 (프로젝트 폴더 기준)

```bash
GODOT="C:/dev/tools/godot/4.7.2/Godot_v4.7.2-stable_win64_console.exe"
"$GODOT" --headless --path . --script res://tests/run_all.gd -- --only=chars                  # 헤드리스 테스트
timeout 120 "$GODOT" --path . res://chars/chars.tscn -- --chars-shots=shots < /dev/null        # GPU 검증 + chars_*.png
timeout 300 "$GODOT" --path . res://chars/scale.tscn -- --chars-scale-shots=shots < /dev/null  # 배율 검증 + scale_*.png + 표
"$GODOT" --path . res://chars/scale.tscn -- --scale=4 --chars-present-check                    # 사람이 데스크탑에서 (아래 "걸린 것")
```

- `--chars-shots`: 걷기 6프레임마다 애니메이션을 멈추고 480×270 렌더 타깃 전체를 CPU 그림과 비교. `CHARS_VERIFY ok ... mismatches=0`이면 종료 코드 0, 아니면 1(다른 프레임은 `chars_expected_f*.png`/`chars_actual_f*.png`로 저장)
- `--chars-scale-shots`: 위 6가지 조합마다 `CHARS_SCALE ok|FAIL ...` 한 줄, 추가 창 크기 표 `CHARS_SCALE_TABLE ...`, 끝에 `CHARS_SCALE_DONE`. 하나라도 어긋나면 종료 코드 1
- 둘 다 렌더러가 필요해서 `--headless` 없이 돌린다(창이 잠깐 뜬다). 내보낸 exe에서는 원본 PNG가 없어 CPU 비교를 못 하므로 프로젝트 폴더에서 돌린다

## 실패하거나 걸린 것

- **표시된 화면(스왑체인)은 직접 읽지 못했다.** 이 데스크탑의 SSH 세션은 Windows 세션 0이라 가상 화면이 1024×768이고 `DisplayServer.screen_get_image()`가 빈 이미지(알파 0)를 준다. 그래서 `scale_<내부>_<창>.png`는 실제 창에서 읽은 렌더 타깃을, 실제 창에서 읽은 Godot 배율·위치로 최근접 확대해 다시 만든 그림이다. 근거:
  - viewport 모드는 내부 해상도로 렌더 타깃을 그린 뒤 화면에 복사한다. 4.7.2-stable 소스에서 이 복사(`renderer_compositor_rd.cpp`의 `blit.sampler = ...sampler_create(RD::SamplerState())`)의 샘플러는 기본값이고, 기본값은 mag·min 모두 `SAMPLER_FILTER_NEAREST`다(`rendering_device_commons.h`). 정수 배율 + 최근접이면 픽셀은 정확히 s×s 정사각이다 (Forward+·Mobile 기준. Compatibility(OpenGL) 렌더러는 보지 않았다)
  - 사람이 데스크탑에서 `--chars-present-check`를 돌리면 창을 화면에서 캡처해 다시 만든 그림과 비교한다(`CHARS_PRESENT ok`면 확인 끝). SSH에서는 `CHARS_PRESENT unavailable ...`, 종료 코드 3
- SSH(세션 0)에서는 창이 화면보다 커도 된다(3840×2160 창이 그대로 만들어짐). 반대로 시작할 때 기본 창 1440×810은 1028×749로 줄어든다(배율 2). 데스크탑에서는 모니터보다 큰 창이 안 될 수 있다
- **팔레트 스왑은 엔진 쪽은 되고, 지금 스프라이트가 문제다.** AI가 만든 프레임은 색 인덱스가 없어서 상의 베이지(예: `#eec58d`, `#c89a68`, `#ba895b`)가 얼굴·머리 하이라이트에도 쓰인다. 원본 색으로만 바꾸면 머리에 점이 생겨서, 이 스파이크는 프레임 안 y 17~25줄로 제한했다(셰이더 `band`). 옆모습(동·서)은 팔과 다른 색이 상의를 덮어 일부만 바뀐다(`shots/chars_layers_x3.png` 오른쪽). 게임에서는 상의를 꾸미기 장비 레이어로 따로 그리거나(brief §5.6 ○ 레이어 구조), 기본 몸을 재질별 고정 램프 색으로 정리(인덱스 색)한 뒤 바꿔야 한다. 그러면 셰이더의 `band`는 필요 없다
- **기준점 재는 법이 결과를 바꾼다.** 같은 v02 시트에서 "정확히 같은 색" / "색 허용 60" / "실루엣"으로 재면 3~4프레임에서 1px씩 다르다(정확한 색: 남 몸통 2프레임 x −1, 북 몸통 1프레임 +1. 실루엣: 북 몸통 4·5프레임 −2·−1). AI 프레임은 프레임마다 색이 조금씩 바뀌기 때문이다. 5차 목업 기록("거의 0, 동쪽 4번째 프레임만 위로 1px")은 v01에서 다른 방법으로 잰 값이다. 엔진 문제는 아니다: 기준점은 표(데이터)로 두고 테스트가 시트에서 다시 재서 맞는지만 본다. 게임용 기준점은 사람이 보고 고정하는 편이 낫다
- 북쪽 씨앗주머니는 1~2프레임에서 발 줄보다 1px 아래로 내려간다(몸통 기준점 +1). 처음 CPU 그림 칸이 발 줄에서 끝나 12픽셀이 어긋났고, 칸을 발 아래 8px까지 늘려 맞췄다. 그림은 이상하지 않다
- 캐릭터마다 ShaderMaterial이 따로라 캐릭터끼리 그리기 묶음(batch)이 안 된다. 9명이면 문제 될 수 없는 수다
- 내보낸 exe에서 `--screenshot=` 상대 경로는 현재 폴더가 아니라 exe 폴더(`build/`) 기준이었다 (스켈레톤 참고 사항)

시험하지 않은 것: 움직이는 카메라(viewport 모드에서는 화면이 1 아트 픽셀씩 움직인다), y-sort 부모 아래의 레이어 캐릭터, 64×64 동작 칸(R26)과 idle, UI 글자의 크기.

## 권장 (화면 배율, 사람이 정할 것: game-concept §7 미결 "화면 배율")

**640×360 내부 해상도 + 정수 배율 + viewport 모드**를 권한다.

- 16:9의 흔한 크기 넷(720p 2배, 1080p 3배, 1440p 4배, 4K 6배)을 모두 테두리 없이 채운다. 480×270은 1080p·4K만 꽉 차고 1440p(5배)에 80×45, 720p·768p에 큰 테두리가 남는다
- 보이는 땅이 40×22.5타일로 480×270(30×16.9)보다 78% 넓다. 9명이 3×3 제단 둘레와 안전 반경 안에 함께 있는 화면에 여유가 있다
- 1080p에서 캐릭터 키가 90px(3배)다. concept-art-brief §7은 480×270을 1080p에 띄운 4배를 실제로 보고 "3배 판정이 실제에 가깝다"며 표식을 3배에서 판정했다(6·7차: 3배에서 씨앗주머니가 세 방향 모두 읽힘). 640×360은 1080p에서 정확히 3배라 그 판정이 곧 실제 화면이다. 대신 북극성 도트 재현(480×270, 1080p 4배)보다 캐릭터가 작게 보인다. 1080p에서 4배의 큰 도트감이 더 중요하면 480×270을 남긴다
- Steam Deck(1280×800)은 640×360 keep이면 위아래 40px 테두리, expand면 640×400으로 꽉 찬다. 16:10·울트라와이드를 expand로 할지는 따로 정한다(울트라와이드 expand는 53.75타일까지 보여 준다)
- 640×360으로 정하면 `project.godot`의 `display/window/size/viewport_width/height`를 640×360으로, 창 기본값을 1920×1080(3배)로 바꾸도록 스켈레톤에 요청한다. 이 모듈은 실행 중에만 바꿨다

## 판정

- 레이어 캐릭터(순서·기준점·반전·떠 있는 후광): **strong**. 노드 몇 개와 표 하나로 되고, GPU 결과가 CPU 기준 그림과 픽셀까지 같다
- 정수 배율 픽셀 퍼펙트: **strong**. Godot가 고른 배율이 모든 조합에서 정수·정사각이고, 내부 렌더는 원본 픽셀 그대로다. 화면 복사가 최근접이라는 것은 소스로 확인했고, 데스크탑에서 캡처 확인 명령 한 줄이 남았다
- 팔레트 스왑: 엔진 **strong**, 지금 에셋 **weak** (인덱스 색이 아니라서 범위 제한이 필요하고 옆모습은 일부만 바뀜)

모듈 전체: **strong** (걸린 것은 엔진이 아니라 에셋 파이프라인 쪽이다).
