# tiles: Wang(코너) 오토타일, 부서지는 벽, 타일 레이어

시험일 2026-10-18, Godot 4.7.2 stable (official, ed1daf0bf), Windows 11 데스크탑(Ryzen 9 9950X3D, RTX 5090), SSH 세션에서 Git Bash로 실행.

## 시험한 것

요구사항: 16px 타일 / 우리 PixelLab 타일셋의 Wang(코너) 오토타일 / 부서지는 벽 / 타일 레이어 여러 장 / 에이전트가 CLI에서 헤드리스로 전부 할 수 있을 것.

쓴 그림 (`res://art/tiles/`, 저장소 `assets/concept/`의 우리 PNG·JSON 사본, 모두 합쳐 약 55KB):

| 타일셋 | 그림 | 모서리 정보 | 지형 |
|---|---|---|---|
| 풀밭↔일군 흙 | `tiles_grass-soil_v03.png` (16장) | `tiles_grass-soil_v01.json` | lower = 흙, upper = 풀 |
| 풀밭↔오염 | `tiles_grass-corruption_v05.png` (16장) | `tiles_grass-corruption_v02.json` (03-pixel) | lower = 재(오염), upper = 풀 |
| 던전 바닥↔벽 | `tiles_dungeon_v02.png` (25장) | `tiles_dungeon_v01.json` | lower = 바닥, transition = 벽 앞면, upper = 벽 윗면 |
| 속 타일 변형 | 풀 4, 흙 2, 재 3, 던전 바닥 3·벽 윗면 2 | (없음, 네 모서리 같은 지형) | 확률 0.25 |
| 광맥 | `tiles_ore_copper_a_v02.png`, `tiles_ore_iron_a_v02.png` | | 벽 윗면과 다른 픽셀만 떼어 덧칠 타일로 |

1. **TileSet 만들기** (`tiles/build_tilesets.gd`, 헤드리스 도구 스크립트): PNG + JSON(`tileset_data.tiles[].corners`, `bounding_box`, `pattern_4x4`)에서 `tiles/tilesets/surface.tres`(풀·흙·재 3지형, 소스 11개, 타일 41장)와 `dungeon.tres`(바닥·앞면·벽 3지형, 소스 3개, 타일 33장, 물리 레이어 1)를 만든다. 같은 입력이면 같은 파일이 나온다(두 번 돌려 md5 같음, 테스트가 새로 만든 결과와 커밋된 파일을 비교).
   - 한 TileSet이 두 방법을 다 받는다: (a)용 terrain set 0(Match Corners) 모서리 비트, (b)용 사용자 데이터 `wang_corners`·`wang_pattern`·`wang_name`·`role`
   - Godot terrain은 타일마다 가운데 지형이 필요한데 코너 타일에는 없다. 그래서 기본 타일은 모서리 다수 지형, 나머지 모서리 지형마다 대체 타일(alternative)을 하나씩 더 만들어 풀이기(solver)가 모든 선택지를 갖게 했다
   - 던전 25장에는 모서리가 같은 짝이 4쌍 있다(JSON `pattern_4x4`가 위·아래 꼭짓점까지 보는 문맥 타일, 예: 벽 기둥의 윗머리). (a)는 이걸 구별할 수 없어서 문맥이 가장 적은 타일에만 terrain 비트를 줬다
   - 광맥 덧칠 2장과 충돌용 "solid" 타일 1장은 스크립트가 그려 `.tres` 안에 무손실로 넣는다(`PortableCompressedTexture2D`, `keep_compressed_buffer = true`가 없으면 에디터 밖에서 저장할 때 데이터가 빠진다)
2. **놓고 부수는 방법 두 가지**
   - **(a) Godot 내장 terrain** (`tiles/terrain_grid.gd`): 셀 = 월드 칸. `TileMapLayer.set_cells_terrain_connect()`로 칠한다. 채울 때는 가장 많은 지형을 `set_cell()`로 먼저 깔고 나머지 지형만 terrain으로 칠한다(아래 "걸린 것" 참고)
   - **(b) 꼭짓점 격자 = dual grid** (`tiles/dual_grid.gd`, `tiles/wang_lookup.gd`): 게임은 월드 칸마다 지형 하나를 정하고, 그 값이 그림 격자의 꼭짓점이 된다. 그림 레이어를 반 칸(8px) 밀어 두면 그림 칸 (dx, dy)의 네 모서리가 월드 칸 (dx, dy) (dx+1, dy) (dx, dy+1) (dx+1, dy+1)이다. 네 값으로 키(3^4 = 81가지)를 만들어 표에서 타일을 고른다. 4단계 목업을 만든 파이썬 목업과 같은 방식이다. 한 칸을 바꾸면 그 꼭짓점을 쓰는 그림 칸 4개(문맥 타일이 있으면 위아래로 한 줄 더)만 다시 그린다
   - 던전 규칙(두 방법 같음): 월드는 바닥/벽만 정하고, 벽 바로 아래의 바닥 꼭짓점은 앞면(transition)이 된다(`04-env/prompts.md` 4단계 기록의 규칙). 그래서 벽 하나를 부수면 꼭짓점 두 개가 바뀐다
   - 같은 키에 타일이 여럿이면: 속 타일 변형은 위치 해시 + 확률 가중치로(다시 그려도 같은 그림), 문맥 타일은 `pattern_4x4`를 가장 잘 만족하는 것으로 고른다. 그림이 없는 키는 가장 가까운 키의 타일로 그린다(fallback)
3. **레이어** (`tiles/dungeon_map.gd`): Floor(바닥 + 변형, 그림 격자) / Walls(벽 Wang, 그림 격자, (b)에서는 전부 바닥인 칸을 비워 바닥 레이어가 보이게) / Ore(광맥 덧칠, 월드 격자) / Collision(벽 칸마다 보이지 않는 사각 충돌 타일, 월드 격자). 넷 다 같은 TileSet. `break_wall()`·`place_wall()`이 넷을 같이 고친다
4. **데모** `res://tiles/tiles_demo.tscn` (모듈 입구 `tiles.tscn`이 이것을 인스턴스): 실행 중에 만든다. 왼쪽 밭(풀, 일군 흙 덩어리, 괭이질 한 칸짜리들, 오른쪽 오염 가장자리), 오른쪽 던전 방(벽 윗면·앞면·바닥, 2x2 기둥, 1칸 기둥, 위쪽 벽감, 왼쪽 굴, 광맥 4개). `_ready`에서 괭이질 2칸, 동쪽 벽 굴 파기, 구리 광맥 캐기를 해서 스크린샷에 고친 타일이 보인다. M 키 = 방법 바꾸기, C = 충돌 레이어 보기, 마우스 = 밭 흙/재, 던전 부수기/쌓기
5. **테스트** `res://tests/test_tiles.gd` (176 checks): 아래 표의 수치와 함께
   - TileSet: 16px, Match Corners, 지형 3, 소스·타일 수, 텍스처 밖 타일 없음, JSON 모서리 = 사용자 데이터 = terrain 비트, 새로 빌드한 것 = 커밋된 `.tres`
   - (b) 정확성: 지상 81개 키 전부 그린 타일의 모서리 = 꼭짓점(그림 없는 50개 키는 모두 흙+재가 섞인 키이고 가장 가까운 키로 그림), 던전 2x4 바닥/벽 무늬 256개 전부(36개 키가 나오고 21개가 그림 있음, 문맥 타일은 제약을 가장 적게 어기는 것), 벽 기둥 윗머리 타일 선택, 변형 비율·안정성
   - (a) 정확성: 작은 무늬 5개(한 칸, 두 칸, 대각, 체크, 2x2)에서 이음매 0·가운데 지형 유지, 두 지형 노이즈 맵에서 가운데 지형 유지와 이음매 1% 미만
   - 벽 부수기: 두 방법 모두 이웃 타일이 바뀐다, 충돌 타일·광맥 덧칠이 같이 없어지고 물리 질의(intersect_point)로 확인, 테두리·바닥 칸은 안 부서짐. (b)는 다시 쌓으면 원래 타일과 같다
   - 레이어 셋(+충돌)이 함께: 순서, 위치(반 칸 밀림), 칸 수, 광맥은 벽 위에만, 캐도 바닥 레이어는 그대로
   - 데모 장면이 두 방법 모두 만들어진다
   - 성능: 512x512 채우기 + 무작위 한 칸 편집 2,000번을 방법마다 (지상·던전), `TILES_BENCH` 줄로 출력

## 실패하거나 걸린 것

**(a) Godot terrain은 우리 타일셋과 뜻이 맞지 않는다.**
- PixelLab Wang 타일은 "꼭짓점 4개의 지형"이고, Godot terrain은 "칸의 지형(가운데) + 모서리 비트"다. Godot 풀이기는 칠한 칸의 가운데 지형을 지키는 데 필요한 만큼만 꼭짓점을 그 지형으로 바꾼다. 그래서 2x2로 칠한 흙이 16x16 덩어리 하나(꼭짓점 1개)로, 한 칸 칠한 흙도 꼭짓점 1개인데 그 칸의 모서리 하나에 붙어 나온다(칸 가운데가 아님). 데모 밭의 ㄱ자 조각들이 이것이다. 괭이질 한 칸 = 흙 한 칸이어야 하는 농사(gameplay-design §3.8)에 맞지 않는다
- 풀이기가 탐욕적이라 그림이 다 있는 두 지형 맵에서도 이음매가 남는다(0.1%). 던전처럼 앞면(transition) 규칙이 있는 3지형 셋은 "칸 가운데 = 앞면"을 잘 표현하지 못해 이음매가 3만 개 생기고 앞면 조각이 벽 속에 떠 있다(`tiles/shots/tiles_a.png` 오른쪽)
- 결과가 칠한 순서에 달려 있다: 같은 맵을 한꺼번에 칠한 것과 한 칸씩 칠한 것이 다르고, 부순 벽을 다시 쌓아도 처음으로 돌아가지 않는다. 변형 타일은 전역 RNG로 고른다(`seed()`가 다르면 같은 맵의 그림이 달라짐을 확인). 호스트가 타일 변경분만 보내는 온라인 협동에서 피어마다 그림이 달라질 수 있다
- 빈 레이어에 모든 지형을 terrain으로 칠하면 망가진다(32x32에서 이음매 약 600, 가운데 지형 틀림 약 650). 가장 많은 지형을 `set_cell()`로 먼저 까는 우회가 필요했다
- 채우기가 8~18배 느리다(512² 지상 4.8초, 던전 8.5초). 편집도 2~6배 느리다

**(b) dual grid는 맞지만 직접 짜야 한다.**
- 코드: `wang.gd` 118줄 + `wang_lookup.gd` 194줄 + `dual_grid.gd` 134줄. Godot 에디터의 terrain 붓으로는 (b) 데이터를 칠할 수 없다(맵은 절차 생성이라 이번 게임에는 문제가 작다. 손으로 만드는 방은 월드 칸 데이터를 따로 칠하는 도구가 필요하다)
- 그림 레이어는 (W+1)x(H+1) 칸이고 반 칸 밀려 있다. 게임 로직·충돌·광맥은 월드 격자, 바닥·벽 그림은 그림 격자다. 섞어 쓰지 않도록 주의
- 맵 밖은 한 지형(`outside`)으로 본다. 데모 밭 오른쪽 끝의 풀 줄이 이것이다(맵 밖 = 풀)

**타일셋에 빠진 조합 (두 방법 공통, 그림 쪽 일)**
- 지상: 흙과 재가 한 타일에 같이 오는 키(81개 중 50개)는 그림이 없다. 둘은 서로 다른 Wang 셋(풀↔흙, 풀↔재)이라서다. (b)는 가장 가까운 타일로 그리고 (a)는 이음매가 생긴다. 해결 안: 밭과 오염이 맞닿지 않게 하는 규칙(밭은 제단 반경 안, §3.8), 흙↔재 셋을 하나 더 만들기, 또는 오염을 투명 위 자동 타일로 따로 겹치는 레이어(gameplay-design §3.1의 "오염" 레이어, concept-art-brief §5.7 ? 결정과 같은 문제)
- 던전: 바닥/벽 맵에서 나오는 키 36개 중 15개는 그림이 없다. 모두 앞면 꼭짓점이 있는 키이고, 대부분 "앞면 바로 아래가 벽"(벽 사이 바닥이 세로로 한 칸뿐인 곳)이다. 동굴 노이즈 맵에서 그림 칸의 5.8%, 데모 방(편집 전)에서는 3칸. 해결 안: 생성·채굴에서 세로 한 칸짜리 틈을 막기, 빠진 15장을 손으로 그리기, 또는 그 경우 앞면을 생략하는 규칙
- 던전 `t1_6_r3_c6`은 우리 규칙(벽 아래 바닥 = 앞면)에서는 쓰일 일이 없다(모서리가 바닥인데 그 위를 벽으로 요구한다)

**그 밖**
- 앞면은 벽 아래 바닥 칸에 그려지는데 충돌은 벽 칸에만 있다. 앞면 칸을 걸을 수 있게 할지(캐릭터가 앞면 위에 서 보임)는 정해야 한다(Y 정렬·가림과 같이)
- 레이어가 크면 칸 하나 바꾼 뒤의 갱신 비용이 커진다(512²에서 130µs). 한 프레임에 한두 번이면 문제없지만, 폭발·광부 3x3 채굴처럼 많이 바꾸면 한꺼번에 하고 갱신은 한 번만 해야 한다. 큰 맵은 64x64 같은 조각 레이어로 나누는 편이 낫다
- 메모리가 칸당 약 300바이트라 512² 레이어 4장이면 300MB가 넘는다. 맵 데이터는 바이트 배열로 갖고 TileMapLayer는 플레이어 근처 조각만 만드는 스트리밍이 필요하다(호스트도 화면에 보이는 곳만 그리면 된다)
- 헤드리스 측정은 그리기 쪽이 빠진다(더미 렌더러). 실제 렌더는 `--render`로 따로 쟀다
- 프로젝트 설정 요청: 없음

## (a)와 (b) 비교, 권장

| | (a) Godot terrain | (b) dual grid |
|---|---|---|
| 우리 타일 그림과 뜻 | 칸 가운데 지형, 꼭짓점은 풀이기가 추측 | 꼭짓점 = 월드 칸, PixelLab 코너 정의 그대로 |
| 한 칸 괭이질 | 모서리에 붙은 덩어리, 2x2도 덩어리 하나 | 칸 가운데 16x16 덩어리, 2x2는 32x32 |
| 던전 앞면·문맥 타일 | 이음매 많음, 문맥 타일 못 씀 | 규칙대로, 문맥 타일 선택 |
| 결정성 (같은 데이터 → 같은 그림) | 아니다 (칠한 순서, 전역 RNG) | 그렇다 (꼭짓점 + 위치 해시) |
| 512² 채우기 / 편집 | 4.8~8.5초 / 250~450µs | 0.5~0.6초 / 45~180µs |
| 직접 짜는 코드 | 거의 없음 | 약 450줄 |
| 에디터 붓 | 됨 | 안 됨 (데이터 도구 필요) |

**권장: (b) dual grid.** 우리 타일셋이 꼭짓점 기준 Wang 셋이고, 한 칸 = 한 칸으로 보여야 하는 농사·채굴, 같은 데이터에서 피어마다 같은 그림이 나와야 하는 타일 변경분 동기화가 모두 (b) 쪽이다. (a)는 손으로 칠하는 장식 레이어 같은 곳에만 쓸 만하다.

## 판정

**strong** — Godot 4의 TileMapLayer에 우리 PixelLab 코너 타일셋을 그대로 올려, 16px 타일, 레이어 넷, 부서지는 벽(충돌·광맥 같이), 반 칸 밀린 dual grid 그리기가 모두 헤드리스로 만들고 시험된다. 512² 맵을 0.5초에 채우고 편집 한 번이 0.2ms 안이다. 내장 terrain(a)은 이 게임에 약하지만 직접 짠 (b)가 450줄 남짓이라 엔진 선택을 막지 않는다. 남은 일은 엔진이 아니라 그림(빠진 조합)과 설계(앞면 칸 통행, 맵 조각·스트리밍) 쪽이다.
